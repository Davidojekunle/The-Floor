# The Floor: web app (v2)

The new frontend, built to the v2 design. It lives beside the original `frontend/` folder so the two don't conflict; nothing here changes `frontend/`.

## Run it

```bash
# 1. Backend (from the repo root)
docker compose up -d
cd backend && uvicorn app.main:app --reload    # http://localhost:8000

# 2. This app
cd frontend-v2
npm install
npm run dev                                    # http://localhost:5174
```

The dev server proxies `/api` to `http://localhost:8000`, so you don't need to change the backend's `CORS_ORIGINS`. Both frontends can run at the same time (`frontend/` on 5173, this one on 5174).

Want demo data? Run `python -m scripts.seed` in `backend/`. The password for every seeded account is `password123`.

## Scripts

| Command | What it does |
|---|---|
| `npm run dev` | Start the dev server on port 5174 |
| `npm run build` | Type-check and build to `dist/` |
| `npm run lint` | Lint with oxlint |
| `npm run types` | Regenerate `src/api/schema.d.ts` from the running backend's OpenAPI schema |

## Structure

```
src/
  api/          fetch wrapper (switches on error.code) and one file per API area
  auth/         token storage, auth context and provider (clears the query cache on sign-out)
  components/   shared UI: AppBar, Menu ("…"), Dialog, toast, Avatar, Icon
  lib/          dates (profile timezone, end-of-day due dates), labels
  room/         room provider and permissions (useCan), stage actions, shared error handling
  pages/        one file per screen
  styles/       tokens.css (colours, fonts), base.css, components.css, app.css
```

## Screens

| Route | Screen |
|---|---|
| `/login`, `/register` | Sign in / create account |
| `/rooms` | Your rooms, new room, open an invite link |
| `/join/:code` | Invitation: ask to join, request sent, invalid link |
| `/my-work` | Your stages across all rooms (list), and a month calendar of your tasks or everything |
| `/rooms/:id` | Room home: needs your attention, your stages, tasks |
| `/rooms/:id/calendar` | Room calendar (month grid; dots and a day list on phones) |
| `/rooms/:id/tasks/new` | New task with stages, stage due dates and templates |
| `/rooms/:id/tasks/:taskId` | Task detail: stage timeline and actions |
| `/rooms/:id/tasks/:taskId/edit` | Edit task: fields, stages, order, parallel, due dates |
| `/rooms/:id/templates` | Templates list, new and edit (`task.create`) |
| `/rooms/:id/members` | People and tags |
| `/rooms/:id/requests` | Join requests (`join.manage`) |
| `/rooms/:id/settings` | Invite link (`invite.manage`) |

"Your stages" on the room home comes from `GET /me/tasks?room=…` (see `src/room/useMyStages.ts`). `src/api/schema.d.ts` is generated by `npm run types`; the hand-written types in `src/api/*.ts` match it and are what the code imports.

## Design rules

Follow the `floor-ui` skill in `.claude/skills/floor-ui/`. It covers user flows, the design system, what the backend actually returns, and known contradictions. In short:

- Gate actions with the room's `permissions[]`, never with `my_role`.
- Use the tokens in `styles/tokens.css`, never raw colours.
- One primary action per screen. Secondary actions go in a "…" menu.
- Confirm destructive actions in a dialog, never with `window.confirm`.
